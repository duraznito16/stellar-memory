# stellar-memory — build roadmap for the "CLI Plugins for Agents" bounty

**Thesis.** The bounty rewards *installable, reusable tooling that makes agents more effective*. You already have the installable part (`bin: stellar-memory`, npm-publishable, an MCP server with 7 tools, a working demo vault). What you do not yet have is a memory an agent can *trust*. A judge who opens the demo and finds one confidently-stated false fact will discount the whole graph — and I verified four such facts by executing your shipped parser.

So the ranking below is not "most missing facts first." It is **stop being wrong → then add the facts that only a Soroban-aware tool could add → then everything else.** Two of the four wrongness fixes are under two hours each and they are also the highest-value new facts, which is the happy case.

One correction to the premises I was handed: several gap write-ups claim `signals()` uses a name-prefix regex (`/^(set|add|…|upgrade|init)/`) at `query.ts:273`. It does not. `signals()` derives "mutating" from `writes`/`emits` **edges** (`query.ts:267-270`), and the comment at `query.ts:262-266` says the name-prefix version was removed *because* it flagged `payroll_address` as a mutation. That precedent is the design rule for everything below: **a signal fires on structural evidence, never on a name.**

## (a) Do now

Five workstreams. Roughly **4–5 developer-days**. Every one is a literal Soroban/Stellar token, read-only, and visible in a 3-minute demo.

### A1 — Make the TTL signal true, and make it say how long you actually have
**Effort: 0.5 day.** Fixes W1 + W2.

**Build.** In `parseStorage` (`rust.ts:419-440`), replace the enumerated method alternation with a generic `(\w+)` capture and classify the result (`get|try_get|has` → read, `set|update|remove` → write, `extend_ttl|extend_ttl_with_limits|extend_ttl_to_max|bump` → ttl, anything else → `unknown`, which emits no edge). Enumeration is why a correctly-written contract is reported as broken; a generic capture plus classification means the next SDK method never silently disappears.

Then branch on durability for argument shape: `instance().extend_ttl(threshold, extend_to)` has **no key** — record it as a contract-level `instanceTtl` fact, not a storage node. `persistent()/temporary().extend_ttl(&key, threshold, extend_to)` keeps arg 0 as key and captures args 1 and 2, which `rust.ts:430` already slices and then throws away.

**Files.** `src/scanner/rust.ts` (`parseStorage`, `StorageAccess`); `src/core/types.ts` (`StorageData` gains `ttlThreshold?`, `ttlExtendTo?`); `src/core/query.ts` (`signals`, `contextDigest`); `src/store/render.ts` (`renderStorage`); `src/commands/mcp.ts` (`storage_layout`).

**Then the payoff:** convert ledgers to time in the message using two hardcoded constants — 17,280 ledgers/day and `max_entry_ttl` = 3,110,400 (~180 days). The demo's `Treasury.fund` does `extend_ttl(&key, 100_000, 200_000)`, so the memory can say: *"`DataKey::Balance(token)` is extended to ~11.6 days when its TTL drops below ~5.8 days — the network ceiling is ~180 days."* No network call, no staleness, and it is not a fact any generic repo tool can produce.

**Why this bounty.** `project_signals`' description (`mcp.ts:194-196`) sells the TTL warning by name. It is your flagship agent-facing signal and it currently both false-positives and pollutes `storage_layout` with a node called `100`.

### A2 — `requiresAuth: boolean` → *whose* authority, plus whether that gate is tested
**Effort: 1 day.** Fixes W3. This is the single most demo-able change on the list.

**Build.** In `parseImplFunctions`, capture the receiver expression of each `.require_auth()` / `.require_auth_for_args()` and resolve it against machinery that already exists: `parseParams` output and `collectLetBindings` (`rust.ts:449-461`, already used by `canonicaliseKey` to resolve exactly the multi-line `let admin: Address = env.storage().instance().get(&DataKey::Admin)…` shape). Classify each subject as:

- `param` — a caller-supplied `Address` argument
- `storage` — loaded from a storage key (record *which* key)
- `current_contract` — `env.current_contract_address()`
- `unknown`

`FunctionData.authSubjects: { expr, origin, key?, forArgs }[]`. Verified on the demo: `Payroll.pay` → `storage / DataKey::Admin`; `Treasury.withdraw` → `storage / DataKey::Payroll`; `Treasury.initialize` → `param / admin`. Today all three render identically as 🔒.

**Change the claim, not just the data.** `render.ts:167-170` must stop asserting access control and instead state the fact: *"Authorizes `admin`, a caller-supplied parameter — this does not restrict who may call it."* / *"Authorizes the address stored at `DataKey::Payroll`."*

**New signal — scope it narrowly.** Do **not** fire on every param-subject auth: `transfer(from, to, amount)` calling `from.require_auth()` is correct SEP-41 and firing there would re-create the `payroll_address` mistake the codebase already learned from. Fire on one hard conjunction only:

> a function that **writes** an instance-storage key it did **not** load, whose **only** auth subject is a caller-supplied parameter, and where no `storage().instance().has(&…)` guard appears in the body.

That is precisely `Treasury::initialize` and `Payroll::initialize` in your own demo, and it is structural, not nominal.

**Ride-along (30 min each, same pass):**
- `env.deployer().update_current_contract_wasm(` → `ContractData.upgradeable = true` + `upgradeFn`. One regex; "is this contract mutable" is the fact that gates every other decision, and `deployer()` appears nowhere in the scanner today.
- `__constructor` flag (already parsed as a normal `pub fn` — probe D confirms `_` is a word char) + the `has()`-then-`panic_with_error!` re-init guard.
- **`mock_all_auths` in tests.** `indexTests` (`scan.ts:590`) already has the test file's source in hand and uses it for exactly one regex. Add `TestData { mocksAllAuths, mockAuths, shouldPanicCases }`. Your demo uses `env.mock_all_auths()` in `treasury/src/test.rs:9,26,46`. Pairing this with A2 produces the strongest sentence in the whole tool: *"Treasury has 3 tests; all of them blanket-mock auth, so the authorization surface is untested."* That qualifies **two** signals `signals()` already emits and costs about 30 lines.

**Files.** `src/scanner/rust.ts`, `src/core/types.ts` (`FunctionData`, new `TestData`, `ContractData.upgradeable`), `src/scanner/scan.ts` (`indexTests`), `src/core/query.ts` (`signals`, `contextDigest`), `src/store/render.ts`, `src/commands/mcp.ts` (`list_contracts`).

**Why this bounty.** An agent asked to add an entry point needs the project's *convention* ("privileged paths auth `DataKey::Admin` from instance storage"), not a boolean. This is the difference between a memory and a symbol table, and `require_auth` is Soroban-only.

### A3 — Fix the trait-impl blind spot
**Effort: 0.5 day.** Fixes W4.

**Build.** `collectContractImpls`: match `impl [<generics>] <Path> [for <Type>]` and file the block under the **implementing type** when `for` is present, keeping the trait path as metadata (`implementsTrait: 'token::TokenInterface'`). `parseImplFunctions`: accept `fn` without `pub` when the block is a trait impl (trait methods are public by definition); keep requiring `pub` in inherent impls so private helpers stay out.

**Files.** `src/scanner/rust.ts` only (plus one field on `ContractData`).

**Why this bounty.** The idiomatic way to write a Soroban token — the most-copied contract shape in the ecosystem — currently renders as *"No public functions detected."* Worse, every downstream signal goes quiet: no auth check on `transfer`, no storage edges, empty `list_contracts`. It is a small fix that removes an embarrassing failure on a very likely judge test case. It is also a hard prerequisite for any SEP-41 conformance claim (B4).

---

### A4 — Error variants, their u32 codes, and the `raises` edge that already exists
**Effort: 0.5 day.** Cheapest new fact on the list.

**Build.** `collectAttributed` (`rust.ts:247-258`) returns `{name, line}` and never opens the enum body — I confirmed both demo error nodes carry `data: undefined`. Parse the body with the existing `matchBrace` helper for `Variant = N`. Emit `ErrorData { variants: {name, code}[] }`. Then emit the **`raises`** edge: `EdgeKind 'raises'` is declared (`types.ts:60`) and labelled in both directions (`render.ts:38,53`) and **no code path anywhere produces it** — the demo index has zero. `FunctionData.returns` already preserves the literal `Result<i128, PayrollError>`, so the edge is a string match against known error-enum names. Finally, consume `spec.errors`, which `spec.ts:80` parses from `udt_error_enum_v0` and `recordDeployment` (`scan.ts:862-875`) discards — diff source codes against deployed codes.

**Files.** `src/scanner/rust.ts`, `src/scanner/scan.ts` (error node payload + `raises` edges + `spec.errors`), `src/core/types.ts`.

**Why this bounty.** Error codes are published ABI; clients match on the integer and a failed invocation surfaces as `Error(Contract, #2)`. Because the vault already fingerprints `node.data` and reports changed nodes per scan (`scan.ts:918-926`), storing the discriminants makes *"someone renumbered `NotAuthorized` from 1 to 3"* an automatically-detected change — you get a second drift detector for almost nothing, on architecture you already built.

### A5 — Stop discarding the token/SAC edge — the value path
**Effort: 1 day.** Three of the supplied gap items (smart-contracts #3, assets #1, assets #5) are **the same twenty lines** in `parseClientCalls`. Treat them as one.

**Build.** Probe C confirms `parseClientCalls` (`rust.ts:511-522`) already yields `["Token", "StellarAsset"]` — detection works. The name then dies at `scan.ts:526-527`: `const target = resolve(client); if (!target) continue;` — no local crate is named `Token`, so the fact is dropped with no node, no edge, no warning. Three changes:

1. Recognise the SDK's built-in clients (`TokenClient`, `StellarAssetClient`, `token::Client`, `token::TokenClient`) as a distinct category from `contractimport!`-generated ones.
2. Capture the **address argument** (`TokenClient::new(&env, &token)` → `token`) and run it through `collectLetBindings`, the same resolver A2 uses, to classify it as caller-supplied param vs. storage-loaded key.
3. Capture the **methods invoked on the binding** (`let sac = StellarAssetClient::new(…); sac.mint(…); sac.clawback(…)`), which are currently nowhere in the output.

Emit an `asset` node (new `NodeKind`) and a `calls` edge instead of dropping it.

**Files.** `src/scanner/rust.ts` (`parseClientCalls`), `src/scanner/scan.ts` (`linkCrossContractCalls` must not silently discard unresolved SDK clients), `src/core/types.ts`, `src/core/query.ts` (`contextDigest`, `signals`), `src/commands/mcp.ts`.

**Signal, scoped honestly.** *"`X.pay` constructs a `StellarAssetClient` and calls `mint`/`clawback` — administrative token powers — with no auth subject resolved to storage."* Say **"names these methods"**, never "holds SAC admin": the scanner cannot establish the latter, and over-claiming here is exactly the credibility failure this roadmap is built to avoid.

**Why this bounty.** `list_contracts` promises "cross-contract calls" and silently omits the most common outbound call in Soroban. A payroll/treasury/DeFi repo leaves **zero** trace that it moves money. An agent editing `Treasury.withdraw` cannot tell from memory that real value crosses a boundary there.

## (b) Do if time allows

Ranked. Each is real; none is worth delaying (a).

**B1 — Event shape: topic tuple + data payload (0.5–1 day).** `parseEvents` (`rust.ts:483-495`) takes `splitTopLevel(args,',')[0]` and `eventName()` reduces it to the first symbol literal — probe E confirms `publish((Symbol::new(&env,"paid"), employee), amount)` becomes the string `"paid"`, dropping the `employee` topic and the `amount` payload; the demo's five event nodes all carry `data: undefined`. The on-chain half is nearly free: `spec.ts:32-39` already types `prefix_topics`, `data_format`, and `params[].location: 'topic_list'|'data'`, and `scan.ts:869` deletes all of it with `events: spec.events.map(e => e.name)`. Deleting that `.map` is a ten-minute change. Topic arity and order are what a `getEvents` filter is built from segment by segment. *Reason it is (b), not (a):* a returning developer is one file-open away from the answer, and it breaks indexers rather than the developer.

**B2 — Deploy scripts: read the file, emit the `deploys` edge (1 day, with a hard scope limit).** `indexScripts` (`scan.ts:654-672`) is synchronous and never calls `readFileSafe` — it writes a node whose entire content is a filename and the constant string `"Build or deploy script."` Deploy order, target network, source identity and alias→crate mapping are exactly the operational facts that evaporate in three weeks. **But read your own demo before designing the parser:** `scripts/deploy.sh` wraps the call in a bash function, so the literal text is `--alias "$name"`, `--network "$NETWORK"`, `NETWORK="${1:-testnet}"`. A naive line-parser will confidently record an alias called `$name`. Scope it to: (i) the ordered list of `stellar contract build|deploy|install|invoke` invocations with raw argument text; (ii) resolution of simple `VAR=literal` and `${N:-literal}` defaults only; (iii) a `deploys` edge **only** when a `--wasm` path or `--alias` resolves to a known crate; (iv) never present an unresolved `$var` as a value. That still gives you deploy *order* — treasury → employee-registry → payroll — which nothing else in the tool knows.

**B3 — Hardcoded `C…` contract IDs and `CODE:ISSUER` assets (1 day).** The only strkey regex in the codebase is `cli.ts:154`, parsing `alias ls` output; deployment nodes have exactly one origin (`listAliases`), and `scan.ts:790` admits the limitation in its own warning text. A repo that pins IDs in `.env`, a test fixture or a frontend config has its entire on-chain half invisible. **Take the defensible half only:** `C[A-Z2-7]{55}` and `CODE:ISSUER`. Skip bare `G[A-Z2-7]{55}` (test seeds and doc examples make it noisy) and skip "network inferred from an adjacent `--network` flag" (fragile). Mark these nodes `provenance: {source:'source'}` and reconcile against alias-derived ones rather than merging. `stellar contract id asset` is pure deterministic derivation and signs nothing, so it stays inside the `cli.ts` read-only boundary.

**B4 — SEP-41 conformance labelling (0.5 day, *after* A3).** A pure set comparison over data you already collect: new `src/stellar/standards.ts` with the interface tables, `ContractData.conformsTo`. Guard it with a threshold — only claim "SEP-41, missing `burn_from`" when the contract already matches most of the interface, otherwise every contract with a `balance` function gets mislabelled. Prefer the compiled spec from `fetchInterface` over the parsed `pub fn` list when both exist.

**B5 — Live instance state via `stellar contract read` (1 day, online-only).** `cli.ts` has four on-chain readers and no ledger-entry reader. Reading the instance entry (no `--key`) returns the executable (`stellar_asset` for a SAC vs. a Wasm hash), the full instance-storage map, and the live-until ledger. Two genuine wins: a SAC currently reports `drift: 'unknown'` and is indistinguishable from an unreachable contract; and the static TTL warning becomes *"instance entry expires at ledger N."* **Report it as observed live configuration, never as "config drift"** — the repo holds no baseline for values set by an init *transaction*, so there is nothing legitimate to diff against. Deprioritised because it only fires when deployed + aliased + online, and SCVal decoding is new surface.

**B6 — Honesty fix on `project.networks` (1 hour).** Fixes W5. Either rename the field to `networksScanned`, or record only networks where something was actually found. `render.ts:224-225` currently states a CLI flag default as a discovered project fact. One hour, removes an assertion the tool cannot support.

## Risk register: things in (b) that would make the tool *newly* wrong

The four wrongnesses in §0 are inherited. These are ones you would be **introducing**, so pre-commit to the mitigation before writing the code:

1. **B2, deploy-script parsing → phantom values.** Your own demo yields `--alias "$name"`, `--network "$NETWORK"`, `--wasm "target/wasm32v1-none/release/${2}.wasm"`. Recording those as the alias, network and artifact would be a brand-new class of confident falsehood, in the one section a judge is most likely to spot-check. Mitigation: resolve only literal assignments and `${N:-literal}` defaults; render anything unresolved as *"argument is a shell variable, not resolvable statically"*; emit the `deploys` edge only on a resolved match.
2. **B3, strkey harvesting → test fixtures as dependencies.** A `C…` in a test file is not an external dependency of the project. Mitigation: record the file kind on the node, exclude `#[cfg(test)]` files and anything under `tests/` from the "external dependency" framing, and keep source-derived deployment nodes distinguishable from alias-derived ones by provenance rather than merging them.
3. **A5, SAC powers → over-claiming.** "This contract can freeze and seize user tokens" is not established by seeing the token `clawback` in a source file. Say what you observed: it constructs a `StellarAssetClient` and names `clawback`.
4. **A2, the auth signal → firing on correct SEP-41.** `from.require_auth()` inside `transfer` is a `param` subject and is entirely correct. The conjunction in A2 (writes an unloaded instance key + only param subjects + no `has()` guard) exists specifically to avoid this. Test it against a real SEP-41 token before shipping; if it fires there, tighten it or ship the *fact* without the *signal*.
5. **B4, conformance → mislabelling.** Any contract with `balance` and `transfer` will partially match SEP-41. Threshold it, and prefer the compiled spec over the parsed source.

## Suggested sequence and the demo it buys you

**Days 1–2:** A1 + A3 (both pure `rust.ts`, both remove wrong output, both under a day). **Days 2–4:** A2 including the `mock_all_auths` and `update_current_contract_wasm` riders. **Day 4:** A4. **Day 5:** A5. Then B1 (cheap), B6 (one hour), and B2/B3 only if the schedule genuinely holds.

That leaves you demoing a `resume` output that reads, on your existing demo repo, roughly:

> `Treasury.initialize` authorizes `admin`, a caller-supplied parameter, and writes `DataKey::Admin` with no re-initialization guard — anyone can call it and become admin.
> `Treasury` has 3 tests; all of them call `env.mock_all_auths()`, so the authorization surface is untested.
> `DataKey::Balance(token)` is extended to ~11.6 days when its TTL drops below ~5.8 days; the network ceiling is ~180 days.
> `DataKey::LastPaid(employee)` is persistent and never extended — it expires and becomes unreachable.
> `PayrollError`: `NotAuthorized = 1, UnknownEmployee = 2, AlreadyPaidThisPeriod = 3, NotInitialized = 4` — public ABI, matched against the deployed spec.
> `Payroll` is not upgradeable — no `update_current_contract_wasm` anywhere in the workspace.

Not one of those sentences is producible by a generic repo-summarising tool, every one is a hard fact with a `file:line`, and each is reachable through the MCP tools an agent already calls. That is the bounty, argued in six lines.
